# Synthea analytics packs (P0, P2)

Synthetic patient data generated by [Synthea](https://github.com/synthetichealth/synthea), flattened to Parquet and DuckDB for the L13 analytics story (`demos/analytics-10k`). No real patient data. Every patient row has `synthetic = true` and `tag = 'HTEST'`.

| Pack | Patients | Seed | Where |
| --- | --- | --- | --- |
| P0 `synthea-analytics-100` | 100 living (+ deceased records Synthea keeps) | 100 | Committed: `fixture-100/` (Parquet + `MANIFEST.json`, about 350 KB) |
| P2 `synthea-analytics-10k` | 10,000 living (+ deceased records) | 20261112 | GitHub Release asset, unpacked to `~/.cache/medplum-demos/synthea-analytics-10k` |

Both packs contain planted data-quality anomalies for the agent to find. What they are and where they sit is in the private answer key (`answer-keys://analytics-10k/`, a separate private repository that is not created yet). Do not commit answer keys, or the step that plants them, to this repository.

Pinned versions are in `pack.yaml`: Synthea v3.3.0 (jar sha256 checked), seeds, reference and end date 2026-10-01, Massachusetts, DuckDB 1.1.3.

## Install (environment build time)

```
demos/_shared/data-packs/synthea-analytics/install.sh            # Java 17+, Synthea jar, DuckDB (Python + CLI)
FETCH_P2=1 demos/_shared/data-packs/synthea-analytics/install.sh # also fetch and verify P2
```

`install.sh` installs `openjdk-21-jre-headless` with apt if Java is missing, downloads the pinned Synthea jar to `~/.cache/medplum-demos/synthea/` and checks its sha256, installs `duckdb==1.1.3` with pip, and puts the DuckDB CLI in `~/.local/bin`. It reaches github.com and pypi.org, so run it while building the environment, never during a demo.

`fetch.sh` downloads `synthea-analytics-10k.tar.gz` from the prerelease `data-p2-synthea-analytics-10k-v1` on gbriggs-cursor/medplum, checks the sha256 in `pack.yaml`, unpacks it, builds `analytics.duckdb`, and runs `verify.py`. It was run end to end against the published URL on 2026-11-12 (output in `evidence/fetch-verify-release-run.txt`). To use another copy, set `L13_P2_URL` and `L13_P2_SHA256`.

## Build from scratch

```
demos/_shared/data-packs/synthea-analytics/build-pack.sh p0   # about 30 s
demos/_shared/data-packs/synthea-analytics/build-pack.sh p2   # about 3.5 min on 8 cores, 3.4 GB of Synthea CSV
```

Steps: `generate.sh` (Synthea), `flatten.py` (CSV to Parquet, synthesizes `device_readings`), the private plant step, `build-db.py` (`analytics.duckdb` and `MANIFEST.json`), then a reproducible tarball. Without the private plant step (`L13_PLANT_SCRIPT`, `L13_PLANT_SEED`, `L13_ANSWER_KEY`), the pack is built clean and `MANIFEST.json` says `"planted": false`. Two P0 builds with the same inputs produced byte-identical tarballs. Two P2 builds produced the same rows in every table (`EXCEPT ALL` both ways returns 0), but `observations.parquet` and `device_readings.parquet` differed at the byte level, so the P2 tarball sha256 in `pack.yaml` pins one specific build.

Check any pack against its manifest:

```
python3 demos/_shared/data-packs/synthea-analytics/verify.py demos/_shared/data-packs/synthea-analytics/fixture-100
```

## Schema

All tables are in `parquet/<table>.parquet` and in `analytics.duckdb`. Ids are Synthea UUIDs.

| Table | Columns |
| --- | --- |
| `patients` | id, birthdate, deathdate, ssn, first, middle, last, gender, race, ethnicity, address, city, county, state, zip, lat, lon, synthetic, tag |
| `organizations` | id, name, city, state, zip |
| `providers` | id, organization, name, speciality |
| `encounters` | id, start, stop, patient, organization, provider, encounter_class, code, description, reason_code, reason_description |
| `conditions` | start, stop, patient, encounter, system, code, description |
| `observations` | date, patient, encounter, category, code, description, value_num, value_text, units, type |
| `medications` | start, stop, patient, encounter, code, description, dispenses |
| `devices` | device_id, start, stop, patient, encounter, code, description, udi, model |
| `device_readings` | device_id, patient, model, reading_date, reading_time, glucose_mg_dl, units |

Windows: `encounters` and `observations` cover 2023-10-01 to 2026-10-01; `medications` and `devices` are those active in that window; `conditions` keep full history. `device_readings` are daily glucose meter readings from 2025-10-01, synthesized from each meter's patient and their HbA1c history. HbA1c is LOINC `4548-4`.

Example:

```
python3 -c "import duckdb; print(duckdb.sql(\"select count(*) from 'demos/_shared/data-packs/synthea-analytics/fixture-100/parquet/patients.parquet'\"))"
```

## Metrics

### HbA1c control (one definition, shared by L13 and G10)

Every story that reports HbA1c control imports `hba1c-control.sql` (SQL) or `hba1c_control.py` (Python, also a command line that prints JSON). Do not re-implement it.

| Part | Definition |
| --- | --- |
| Results counted | One row per HbA1c observation (LOINC `4548-4`), not one value per patient, with a numeric value and units `%` or `mmol/mol`. Other units are excluded. |
| Headline cohort (`t2dm_value_set`) | Patients with a type 2 diabetes condition in the value set: SNOMED CT `44054006` or ICD-10-CM `E11.9`, matched on system and code. No living-patient filter and no other cohort filter. |
| Naive cohort (`snomed_44054006`) | SNOMED CT `44054006` only. Reported beside the headline for comparison; label it "naive" wherever it is shown. |
| Conversion | `%` rows are used as is. `mmol/mol` (IFCC) rows are converted to NGSP percent with `0.09148 * IFCC + 2.152`. The converted value is not rounded before the threshold. |
| Controlled | Converted value `< 7` (strict). 7.0% is not controlled. |
| Rate | `controlled rows / rows`, per calendar month of the observation date, rounded to one decimal once, after the counts. |
| Raw rate | `control_pct_raw` applies the same threshold to the value as stored, ignoring units. |

Python:

```
python3 demos/_shared/data-packs/synthea-analytics/hba1c_control.py <pack_dir> --from 2026-02 --to 2026-03 --cohort all
python3 demos/_shared/data-packs/synthea-analytics/test_hba1c_control.py   # definition cases; pack values only with the private key
```

`hba1c_control.monthly(con, start, end, cohort=HEADLINE)` returns rows with `cohort, month, n, mmol_rows, controlled_n, control_pct, controlled_raw_n, control_pct_raw`. Pass `cohort=SNOMED_ONLY` for the naive cohort or `cohort=None` for both.

SQL: create tables or views named `observations` and `conditions` (the schema above), then run `hba1c-control.sql`. It creates temp objects `hba1c_t2dm_value_set`, `hba1c_ngsp_pct(v, u)`, `hba1c_cohorts`, `hba1c_results`, `hba1c_control_monthly_by_cohort` (both cohorts, one row per cohort and month) and `hba1c_control_monthly` (headline cohort only). Temp objects load into a read-only `analytics.duckdb`.

Pinned per-pack values are not in this repository. They live with the private answer key (`answer-keys://analytics-10k/`, `expected-metrics.json`); `test_hba1c_control.py` reads them from there when present and otherwise checks only that the views load.
